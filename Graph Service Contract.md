# Контракт сервиса зависимостей графа

Этап 3.1 определяет только интерфейс `IGraphDependencyService` и типы `DependencyValidationResult` / `DependencyValidationError`. Реализация проверок и вычисления блокировки добавляется в этапах 3.2–3.4. Сервис пока не регистрируется в DI и не подключается к API.

Рабочая ветка этапов 3.1–3.5 — `graph-logic`, созданная от `dev` на коммите `57d3d1f`. На момент начала работ ветка сущностей `domain` ещё не включена в `dev`: для локальной сборки её файлы взяты из коммита `e7fa5cc` без нового коммита. Перед PR бизнес-логики необходимо сначала влить `domain` в `dev` и обновить рабочую ветку, чтобы сущности не попали в повторный коммит.

## Входные данные

`ValidateDependency` принимает кандидат `TopicDependency`, коллекцию тем `IReadOnlyCollection<Topic>` и коллекцию существующих рёбер `IReadOnlyCollection<TopicDependency>`. Кандидат рассматривается как ребро `PrerequisiteTopicId → TopicId`. Если такая пара уже есть в существующей коллекции, это дубликат.

`GetBlockedTopics` принимает те же коллекции без кандидата и возвращает `IReadOnlyDictionary<Guid, bool>` с результатом для каждой переданной темы.

Коллекции могут содержать несколько роадмапов. ID тем уникальны во всей переданной коллекции. Для каждого существующего ребра обе темы должны быть переданы, а их `RoadmapId` должны совпадать с `RoadmapId` ребра. Существующие рёбра не содержат повторных пар и самозависимостей; статусы тем входят в `StudyStatus`.

Вызывающий код передаёт все существующие рёбра обрабатываемых роадмапов и все темы, на которые они ссылаются. Определить, что часть сохранённых в БД рёбер не передана, сервис без хранилища не может. Отсутствующая тема кандидата является обычной причиной отказа, а отсутствующая тема существующего ребра — повреждённым входным графом.

Существующий граф предполагается ацикличным. `ValidateDependency` проверяет появление цикла от одного нового ребра и не заменяет полный аудит ранее сохранённых данных. Корректность начального графа обеспечивает вызывающий код. Рёбра других роадмапов не должны влиять на поиск пути в роадмапе кандидата.

## Ошибки входных данных

Перед проверками кандидата реализация должна проверять структурную корректность переданных аргументов:

| Нарушение | Поведение |
| --- | --- |
| `null` вместо кандидата или любой коллекции | `ArgumentNullException` с именем аргумента. |
| `null` среди элементов коллекции | `ArgumentException` с именем коллекции. |
| Повторный ID темы | `ArgumentException` для `topics`. |
| Недопустимое значение `StudyStatus` | `ArgumentException` для `topics`. |
| Существующее ребро ссылается на отсутствующую тему или другой роадмап | `ArgumentException` для `dependencies`. |
| Повторная пара существующих рёбер или существующая самозависимость | `ArgumentException` для `dependencies`. |

Это будущие обязательства реализации интерфейса, а не уже выполненные проверки. Непустые названия, вес и координаты не влияют на проверку связей; их валидация относится к CRUD и настройке хранения.

## Проверка кандидата

При структурно корректных аргументах причины отказа проверяются последовательно:

| Порядок | Проверка | Ошибка |
| --- | --- | --- |
| 1 | Существование `TopicId`, затем `PrerequisiteTopicId` | `TopicNotFound` с первым отсутствующим ID в `MissingTopicId`. |
| 2 | Обе темы и кандидат принадлежат одному роадмапу | `RoadmapMismatch`. |
| 3 | ID двух тем различаются | `SelfDependency`. |
| 4 | Пары `(TopicId, PrerequisiteTopicId)` ещё нет | `DuplicateDependency`. |
| 5 | Для кандидата `A → B` в существующих рёбрах нет пути `B → A` | `CycleDetected`. |

Если все проверки пройдены, возвращается результат `Success()`: `IsValid == true`, `Error == None`, `MissingTopicId == null`. При отказе `IsValid == false`, `Error` указывает причину. `MissingTopicId` обязателен только для `TopicNotFound`, для остальных ошибок он отсутствует.

Результат неизменяемый и создаётся через `Success()` или `Failure(...)`. Фабрика `Failure` отклоняет `None`, неопределённые значения enum и несогласованное использование `MissingTopicId`.

Операция только проверяет кандидат. Ни успешная, ни неуспешная проверка не добавляет ребро и не меняет коллекции или их объекты. Возвращаемый результат не зависит от порядка элементов коллекций.

## Блокировка и пустые коллекции

Предлагаемое для этапа 3.4 правило: тема заблокирована, если хотя бы одна её непосредственная предварительная тема имеет статус, отличный от `Completed`. При отсутствии предварительных тем блокировки нет. `blocked` не сохраняется в `Topic`, статусы и другие свойства тем не меняются.

Новый вызов вычисляет блокировку по актуальным входным данным без зависимости от предыдущих вызовов. Для пустых коллекций тем и рёбер `GetBlockedTopics` возвращает пустой словарь. Для существующих тем без рёбер возвращается `false` для каждой темы. Проверка кандидата с пустыми коллекциями возвращает `TopicNotFound` для `candidate.TopicId`.

README и описание диаграммы не определяют отдельно транзитивность блокировки и поведение завершённой темы после отмены завершения её prerequisite. До завершения 3.4 нужно уточнить эти случаи с участником В. Интерфейс не фиксирует правило автоматического сброса статусов и не выполняет такой сброс.

Сервис использует сущности Graph и стандартные типы .NET. Контракт не зависит от EF Core, DbContext, HTTP, JWT, RabbitMQ или готовности базы данных.
